## V1.4 — Dating Simulation
###### VARIABLE UPDATE RULES ######
Highest Priority Rule:
  MUST read <CURRENT_VARIABLE_DATA>, <JSONPatch_Format>, <Schema_Syntax> before any reasoning.
  All updates based ONLY on real-time data. Keys/values use story language (English→English, 繁中→繁中).
  check:
    - CURRENT_VARIABLE_DATA is the source of truth. Never assume or reuse outdated values.
    - Partner object keys MUST use English first name. Display name goes in "Name" field.
    - Path keys MUST NOT contain "." or "/" (reserved as delimiters).
      Allowed: Chinese chars, A-Z a-z, 0-9, _, -, #.

OUTPUT FORMAT
  End of EVERY response: output <UpdateVariable> block. No changes → JSONPatch = [].
  check:
    - Must appear at very end. JSONPatch must be valid JSON array.
    - Every op object needs "op" and "path". Keys use normal JSON: "Key":
    - Fields starting with `_` are readonly (e.g. `_var`). Don't update them.
    - Never use "/path" as a key. Never put path string inside "op".
    - Paths must reference existing keys unless using add.
    - Use remove when Qty→0 (Belongings) or quest completed.
    - Validate each op before output:
      1. "op" = replace|delta|add|remove  2. "path" starts with "/"
      3. replace/delta/add need "value"   4. remove has no "value"
      5. Must pass JSON.parse()           6. No unescaped newlines in strings — use HTML tags.
    - Many patch lines → re-check line by line before output.

NUMERIC UPDATE RULES
  Always use replace with final absolute value. If result is 0, use remove.
  Never use delta. Never use +1/-1. Read current value first, calculate, then replace.

TUPLE FIELD RULES
  Fields stored as [value, label]. Applies to strings, numbers, AND booleans.
  check:
    - Only update index 0. Never change label unless explicitly instructed.
    - BOOLEANS ARE TUPLES: [true, "Conflict Active"], [false, "Present"]. Never bare true/false.
    - On Partner creation, every #tuple field MUST use tuple format — no exceptions.
    - Money/Salary are tuples: [value, "Label"]

DYNAMIC WORLD EVENTS RULES
  path: /World_Calc

  check:

    - Named recurring character with meaningful interaction → /World_Calc/NPCs
      See NPC INSERTION THRESHOLD for qualifying conditions.
      REGISTRATION GATE — ALL three conditions must be true:
        1. Has a name AND a defined personality/role beyond a service function.
        2. Has a lorebook entry OR has appeared across 2+ scenes with direct meaningful dialogue.
        3. Is NOT a service/background role (waiter, guard, clerk, shop assistant, passerby, subordinate of a main cast NPC).

        NPC fields: name, relationship, occupation, personality, last_seen, summary.
        NPC calculation traits: Dominance, Confidence, Shyness, Playfulness, Kindness, Patience.
        WHEN TO ADD THE 6 TRAITS:
          - NPC has a lorebook entry OR character profile with personality described → add ALL 6 traits immediately on first registration.
          - NPC qualified via 2+ scenes (no lorebook) → add the 6 traits at registration.
        Map trait values from the personality description using the same 0-100 / -100 to 100 scale as Partners.
      NPC summary = character bio only (who they are). NEVER log scene events or timestamps in summary.
      Scene events → World_Calc.Events. See <Update_Analysis_Detail> step 15 for the enforced rule.
    - New info conflicting with lorebook → record in /World_Calc/Events

  Partner: /Partner/<PartnerKey> — PartnerKey=English first name. Name field=display name. Partner is a COLLECTION.

  TimeSinceLastSeen:
    Format: "YYYY-MM-DD HH:MM". Update ONLY when partner meets/contacts {{user}} this reply.
    Set to current World.Date + World.Time. Don't update absent partners with no contact. Don't compute durations.

BELONGINGS RULES
  Item container for Mainchar and Partner. No stat bonuses. Slot is always "Misc".
  Paths: /Mainchar/Belongings, /Partner/<NameKey>/Belongings
  Fields per item: Type (Gift/Accessory/Consumable/Keepsake/Key Item), Slot ("Misc"), Qty (int), Desc (string)
  Rules:
    - Only update individual item keys. Never overwrite entire container.
    - EVERY item MUST include "Slot":"Misc" — required for equip/unequip to work.
    - BEFORE any op, check if item exists in CURRENT_VARIABLE_DATA:
      Not exists → "add" with complete object: {"Type":"Gift","Slot":"Misc","Qty":1,"Desc":"A dozen red roses"}
      Exists → "replace" at .../Qty with final absolute value (current + gained - spent)
      Qty→0 → "remove" entire item (not just Qty)

SKILLS RULES
  path: /Mainchar/Skills — only Mainchar. Update individual skill keys.

QUEST RULES
  path: /Mainchar/Quests — only Mainchar.
  Fields: Desc, Objective, ProgressSummary, Reward, Status, LastUpdated ("YYYY-MM-DD HH:MM").
  Rules:
    - Desc = quest brief/background. Treat as stable reference text; set on create, do not use for live progress logs.
      DEADLINE RULE: If the source material mentions a relative deadline (e.g. "within two weeks", "by next month",
      "in three days"), convert it to an absolute in-game date using the current World.Date at the moment the quest
      is created. Write the resolved date directly into Desc or Objective (e.g. "Deadline: YYYY-MM-DD").
      Never write relative time ("in two weeks") — only absolute dates.
    - Objective = current concrete win condition. Keep short and testable (what must happen to finish).
      If Objective includes a deadline, it must be an absolute date, not a relative one.
    - ProgressSummary = short running status (2-3 sentences) of what has happened so far.
    - Status should reflect phase (e.g., Active, Blocked, Completed).
    - Completion check runs in <Update_Analysis_Detail> step 14 every reply: if Objective is already satisfied in current scene/data, remove that quest entry.
    - Update LastUpdated whenever Objective, ProgressSummary, or Status changes.
    - No progress/change this turn → do not modify quest fields.
    - Never overwrite entire /Mainchar/Quests; only add/remove/replace individual quest keys.
  Completed quests must be removed.

MEMORY RULES
  Collections with Desc + TimeStamp ("YYYY-MM-DD HH:MM"). FIFO on capacity.
  Paths & limits: PositiveMemories(max 5), NegativeMemories(max 5), ImportantEvents(max 10)
  Key = short label (e.g. "First_Date"). No "." or "/" in keys.
  Before adding: MUST count entries in <CURRENT_VARIABLE_DATA>. At capacity → remove oldest TimeStamp first, then add new.
  See <Update_Analysis_Detail> step 7 for when to create memories.

FRIENDS RULES
  Tracks partner's social circle — named characters she directly interacted with.
  path: /Partner/<NameKey>/Friends — no capacity limit.
  Fields: Name (#string), FriendshipScore (#string, numeric value as string, 0-100, start "10"), Mood (#string)
  Score changes ONLY on direct interaction between the two characters (spoke to each other, acted toward
  each other, helped/clashed). Shared witness of a third-party event does NOT count. Co-presence alone
  does NOT count. See <Update_Analysis_Detail> step 15b for the full decision procedure.
  EXISTENCE CHECK (mandatory before every Friends patch):
    BEFORE writing any op, look up /Partner/<NameKey>/Friends/<FriendKey> in CURRENT_VARIABLE_DATA.
    Not exists → use "add" with complete object. FriendshipScore MUST start at exactly "10", no exceptions:
      {"Name":"<Name>","FriendshipScore":"10","Mood":"<mood>"}
      NEVER set a higher or lower starting score even if the relationship feels established.
    Exists     → use "replace" at the specific field path (e.g. .../FriendshipScore)
    NEVER use "replace" on a Friends entry that is not confirmed present in CURRENT_VARIABLE_DATA.
  Score=0 → "remove" entire entry. Key=English first name. Only update individual keys.

GENERIC CONTAINER RULES
  Containers (Belongings, Skills, Quests, memories, Friends): never overwrite entire container.
  Only add/remove/replace nested entries.

SAFETY RULES
  - Don't invent keys unless using add. Don't modify tuple labels.
  - Missing path → create with add at correct level.
